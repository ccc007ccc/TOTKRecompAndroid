## 定位结果

`profile-a` 在场景就绪后开启 `--profile`，另用 simpleperf 采集 8 秒用户态 CPU cycles，
250 Hz、frame-pointer 调用栈，共 6356 个样本。计数只汇总完全落在有效采样区间内的日志窗口。
CPU cycles 占比是所有被采样线程的合计，不是单帧墙钟占比。

| 每帧诊断量 | 基线，295 帧 | 优化，345 帧 |
| --- | ---: | ---: |
| 顶点复制 | 49.519 MiB | 45.351 MiB |
| 顶点/索引准备 CPU 时间 | 4.912 ms | 4.583 ms |
| 渲染执行 CPU 墙钟，含等待 | 26.634 ms | 25.814 ms |
| GPU 时间 | 27.966 ms | 27.194 ms |
| buffer-copy 等待 | 3.180 ms | 3.232 ms |
| SyncWait 等待 | 6.881 ms | 5.687 ms |
| 按需着色器/管线准备等待 | 0.034 ms | 0.081 ms |

CPU 与 GPU 时间有重叠，不能相加解释总帧时间。诊断运行及不同温度下的耗时不能直接当作帧率收益。
顶点复制量减少 **8.4%**；这是本轮最直接的工作量证据。

基线后台 `shader_warm::prepare` 线程占采样 cycles 的 **33.24%**，渲染线程约 **24.19%**。
调用栈把大量 `vsnprintf`/`__vfprintf` 开销定位到 Maxwell→GLSL 翻译，不能误判为逐帧日志输出。
优化包新身份的首轮采样中后台准备仍占 **37.21%**；普通优先级调低到 nice +10 并不意味着它不消耗 CPU。
GPU 时间也已经明显超过 60 FPS 的 16.67 ms 预算；只优化 CPU 复制不能据此宣称可达 60 FPS。

## 本轮修改

`vc_mark_sbufs()` 原先在着色器存在全局存储时调用 `guest_copy_flush()`，清空所有上传缓存。
实际翻译器 `global_address()` 和 `gwin_prepare()`/`gcopy_prepare()` 仅允许主堆地址，
大量位于 ALIAS 区域的顶点数据也被连带失效，下一次绘制重新上传相同内容。

现在用独立的主堆写入代次标记全局存储：

- 主堆内、跨主堆边界的上传全部失效，包括着色器通过指针访问未绑定 SBUF 的位置。
- 堆外上传可在同一提交内复用；显式 CPU 更新、buffer-copy、全局清空和新提交仍按原契约使缓存失效。
- 复制模式的 `ga_load_copy()` 同样检查主堆代次，不复用全局存储前的旧快照。
- 不删除 GPU 同步，不改变着色器输出，不开启共享映射或异步复制，保留点尺寸/割草修复。

曾试验同地址较短前缀复用，但顶点复制仍为 49.526 MiB/帧，普通测量为 24.37 FPS，
未显示明确收益；该改动已撤回，未包含在最终代码。

异步复制单独开启的普通测量为 24.31 FPS、p95 51.98 ms；诊断显示原来的约 3.18 ms
`buffer -> buffer copy` 等待变成约 3.20 ms `buffer copy CPU dependency`。
等待被后续 CPU 消费重新触发，因此没有据此默认开启这条路径。

优化包另外做了 `--shader-warm off` 普通对照：20.81 FPS、p95 66.15 ms，电池温度 40.1→40.6°C。
此开关同时关闭自动 SPIR-V 准备和管线预热，改变启动期工作分布；单轮结果不能独立量化后台翻译的影响。
本轮保留默认准备行为。后续应分别测量准备预算、按需等待和线程频率，而不是直接删除后台工作。

## 普通帧率对照

下表均为未开启逐帧 profiling 的 15 秒测量。温度为 Android Battery Service 的电池温度，
不与厂商 PhoneTemp/SoC 传感器混用。所有有效运行均由运行时自行退出。

| 运行 | 版本 | FPS | p95 (ms) | 电池温度前→后 |
| --- | --- | ---: | ---: | --- |
| `baseline-a` | 基线 | 24.19 | 51.64 | 38.3→38.4°C |
| `baseline-a2` | 基线 | 22.44 | 59.69 | 40.4→40.1°C |
| `heap-b1` | 优化 | 25.65 | 46.42 | 40.1→40.0°C |
| `baseline-a3` | 基线 | 20.10 | 69.83 | 40.7→40.7°C |
| `heap-b2` | 优化 | 23.09 | 50.52 | 40.9→41.2°C |

两组交替复测均观察到更高帧率和更低 p95；同时旧版本身也从首次 24.19 FPS 波动到 20.10 FPS。
这些短测支持保留本轮优化，但不足以把某一轮差值写成长期、跨场景的固定收益。
当前最确定的结论是减少重复上传；稳定帧率还需控制温度、准备进度和缓存状态后做更长的场景验收。

## 验证与后续重点

- `test_android_upload_caches.py` 执行正式 C helper，覆盖顶点/片元/计算三个阶段的存储、
  主堆内未绑定地址、跨上下边界、堆外保留、明确写入、跨提交、全局清空和 arena 快照失效。
  私有负对照恢复旧的全量失效，堆外复用用例失败。
- 提交快照/资源登记回归通过；驱动常量回归通过，包含点尺寸上限。
- Eden 运行时合成套件通过；Release/8 Elite/perftest 实际构建通过。
- 本轮只做固定草地场景短测，未执行移动/割草路线、长期稳定性或其他设备验收。

剩余重点是 GPU 各 pass 的成本、堆外顶点重复上传的剩余来源、buffer-copy 的真实 CPU 消费依赖，
以及后台着色器准备的计算预算。分别测量后再改，不用降低分辨率、跳过绘制或移除同步掩盖瓶颈。
