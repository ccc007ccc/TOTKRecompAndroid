## 适配内容

- `main`、`sdk`、`subsdk0`、`rtld` 均生成函数表、编译和装载。`subsdk0` 是 multimedia，
  不能当成旧版本 BOTW 中可省略的 NVN 模块。SDK 初始化后依次初始化 multimedia、main、rtld；
  退出回调按相反顺序执行非 SDK finalizer。
- 游戏库 ABI 升为 2，名称为 `totkgame.so`。四个 NSO 的完整 Build ID 写入函数表，
  装载前与实际 ExeFS 比较，检查地址区域重叠。生成缓存同时绑定输入散列和生成器源码。
- `tools/totk.py` 固定四个已核实的 1.4.3 Build ID，检查 NPDM 程序 ID。当前不宣称支持
  未合并更新的 1.0.0、其他 TotK 更新或 BOTW 输入。
- 内核返回 TotK 程序 ID，应用服务返回 1.4.3，NVN 使用 55.15 参数表。BOTW 的地址补丁、
  动态帧率和超宽屏 hook 不会因 TotK 的版本编号而启用。未实现导入调用给出明确错误。
- NPDM 的 24 MiB 系统资源接入 GetInfo，允许 SDK 初始化虚拟地址管理器。物理映射仅清零新页，
  重叠映射保留内容；解除映射支持范围拆分，并更新内存用量，拒绝覆盖其他类型的映射。
- 生成器识别解压器通过 ADR 保存的局部返回地址，让跨条件分支的 BR 在函数内部进行检查后分派。
- 音频渲染工作区大小改为调用原 SDK 计算；`hwopus` 接入原 SDK 的软件 Opus 解码器，
  补齐音频设备名称、音量和事件接口。真机已通过音频初始化；分流器和部分效果器仍未实现。
- 修正存储属性的类型字段偏移，区分账户、设备、临时及带索引的缓存目录，元数据不暴露给游戏文件系统。
  FSP 返回真实缓存列表对象，支持分页快照读取、创建、大小查询和删除；AM 的缓存创建使用同一套目录。
  临时数据首次挂载时清理。未导入的 BOTW 存档探测返回 TargetNotFound，避免继承数据检查中止启动。
- NVN 着色器类型、代码范围和常量范围从 55.15 控制块读取；计算着色器从 `+0x100` 开始翻译，
  不再把头部当成指令。补齐本次遇到的 RED U32/S32、VOTE、VMNMX MIN/MAX 和 LEA.HI 指令形式。
- 打包纹理区分显式零布局与默认布局，解析高度和深度两个参数，忽略 SDK 未使用的高位及第二个字。
- 应用包名为 `com.totkrecomp.android`。数据和存档位于自己的 Android/data 目录。
  Java/JNI 类命名仍保留 `com.botwrecompandroid`；这不影响应用隔离。
- `pull_totk.py` 流式读取手机 NSP；`prepare_totk.py` 合并 BKTR 并生成 RomFS，
  `totk_romfs.py` 导出 FFmpeg 需要按路径读取的视频。部署和启动只使用正常 APK 链路。
- 所有本轮工作数据集中在 `.work/totk-port/`。工具设置 `TMPDIR`、`TMP`、`TEMP`、
  Java 临时目录；部署不再使用 `/data/local/tmp`。私有文件和构建结果不进入 Git。

## 本机验证

- `tools/test_totk.py`：13 项输入、版本隔离、流式提取、NSO 段读取和 RomFS 视频导出检查通过。
- 静态检查发现并补齐主程序 12 处成对独占指令（LDXP/LDAXP/STXP/STLXP）。
  128 位操作覆盖两个数据槽，支持零寄存器、SP、32 位写回及独占失败；宽度或地址不匹配也会清除保留状态。
  SDK 仍有一个条件 MTE `STG` 位置保留明确停止，尚未证明运行可达性。

  测试二进制编译/链接通过，不依赖外部 128 位原子函数。尚未把该测试二进制在手机执行。
- 合并后的 RomFS 为 17,052,625,232 字节，通过 `runtime/romfs_build.c` 的 `romfs_image_ok`；
  304,243 个文件范围均位于映像内；导出 28 个独立视频文件，共 1,609,787,432 字节。
- Debug APK 已构建并在目标手机安装。Activity/JNI 启动器创建了 Adreno 830 的 Vulkan 1.3
  设备与交换链；该结果只证明宿主启动器链路。
- 物理映射的重叠保留、部分解除、重新映射清零、类型隔离和预算检查通过；
  局部间接跳转的生成 C 在两种 guest base 和两个条件分支下执行通过。
- `test_audio_routes.c`：音频路由、音量和事件检查通过。
- `test_save_storage.c`：空列表、分页/快照、AM/FSP 共享目录、重复创建、容量、存储隔离、
  只读挂载、挂载期间删除保护、跨应用存档不存在检查通过。
- `test_totk_shaders.c`：控制块及计算入口检查通过；28 个合成着色器通过 glslangValidator
  和 spirv-val 的 Vulkan 1.3 验证。原 `test_shader_int32.c` 的 253,952 个算术/地址向量通过。
- `test_packaged_layout.c`：builder 存取、显式零、高位屏蔽、2D mip 偏移、3D GOB 边界检查通过。
- 原有 `tools/test_lift.py` 依赖 macOS CommonCrypto 和 ARM64 宿主，不能在本机 x86_64 dev

### 第 45–46 轮：水面反射与光照恢复，用户确认

run45 第 1500 帧完整捕获 204 张附件，210 MiB，无遗漏。水面材质、法线、折射输入与环境图均有内容，

根因是材质筛选使用的深度运算精度不同。水面材质字节 `0x33` 经掩码和半字节交换，得到编码值 50。
片元阶段将编码值写入 D16，水面光照的顶点阶段重算该值，以 EQUAL 比较选择水面像素。
原编译路径只给顶点浮点运算添加 `NoContraction`；片元阶段允许驱动合并运算，
在同一 Adreno 830 / Banner Turnip 上写出 39193，而顶点路径对应 39192，整次水面光照被拒绝。

独立 GPU 小测试复现了同样的运算与筛选，不重启游戏：256 个合成编码中 D16 有 12 个失败，
包含当前水面的 50；D32F 有 24 个失败。因此改用更高位深并不能解决运算差异。
两阶段都保留运算后，D16 / D32F 各 256 个全部匹配。该计数不是游戏缺失材质或效果数量。

`shaders.c` 现在从编译后的 SPIR-V `DepthReplacing` 执行模式识别显式写入深度的片元着色器，
对其应用与顶点阶段相同的运算保留处理；普通颜色片元沿用原策略。更新 Android 和桌面缓存版本，
避免读取旧精度策略下的 SPIR-V。没有绑定固定游戏 shader 地址，也没有放宽 EQUAL 比较。
