# 2026-10-29：真实 2× / 60 FPS 优化

目标是正常 2× 设置下达到 60 FPS，包含转视角。禁止暗中绕过缩放、跳过绘制或只拿静止短测证明达标。
从 `fb8e4ad` 的真实条件基线继续：固定场景约 19.71 FPS，转视角约 18.77 / 19.31 FPS；
诊断窗口 GPU 区间约 40.54 ms/帧，另有编译长帧和温控。详见 [测量口径更正](RELEASE-DIAGNOSTICS-20261029.md)。

## 方向筛选

| 方向 | 当前证据/处理 |
| --- | --- |
| 后台资源争用 | **确认并修复**：切到桌面仍持续绘制、占约 179% CPU；修复后不再持续出帧，后台约 5–6% CPU |
| 长阶段拆分与移动 GPU 带宽 | 真实 2× / 转视角关闭拆分短测 17.99 FPS，p95 68.11 ms；未显示显著收益，保留原默认，不据不同温控的一轮数字断言必然更差 |
| 多附件/高分辨率绘制 | **2026-10-30 确认并修复主要原因**：所有颜色图像因缺少格式列表被 Turnip 关闭 UBWC；补列表后 2× 转视角 GPU 忙碌约 41 → 33 ms/帧，见下文“渲染效率审查” |

| Turnip GMEM/sysmem 选择 | 强制 sysmem 17.54 FPS、强制 GMEM 3.80 FPS；现有通道结构（全附件 LOAD/STORE、频繁打断）基本只能用 sysmem |
| shader 指令与精度路径 | 后续检查寄存器、溢出、64-bit 运算以及慢 shader；先做独立数值/画面对照，再改默认 |
| 编译与准备竞争 | 关闭自动预热的 2× 转向短测为 18.27 FPS，p95 67.35 ms；未出现大幅收益，保留默认，继续区分首次编译与稳态瓶颈 |
| 缓存持久化 | 原始 Vulkan driver cache 已按 UUID/vendor/device 验证，未错误绑定整个运行时提交；不再重复设计第二套缓存。准备 recipe 的身份另行分析 |

原始证据统一放 `.work/performance-2x60-20261029/`，不提交游戏输入、捕获与 APK。

## 后台持续渲染

SDL 3.4.16 Android 默认会在生命周期事件入队后阻塞自己的事件线程。
项目此前在 `SDL_PollEvent` 返回后才处理后台通知，并且游戏/渲染线程独立于 SDL 事件线程。
没有窗口时仅跳过最终呈现，之前的游戏绘制和 GPU 提交仍持续执行。

在独立测试包加载同一存档，恢复运行后按 Home：后台稳定区间约 **178.60% CPU**（单核 100%），
5.11 秒内日志帧号从 873 增到 935，仍每帧数千次绘制。因而手动切换两个包可能留下争用资源的后台实例，
但尚不能据此断言用户每次普通 Release 个位数帧都由这个问题引起。

实现：

- 使用 SDL event watch，在 SDL 阻塞前发布前后台状态；回调只请求预热取消，不在 SDL 派发锁中 join worker。
- guest 生产者在已排队的 present 后、帧边界睡眠，允许在途工作完成。等待时释放内核 core-0 所有权，避免阻塞其他 guest 线程的收尾。
- 回前台广播唤醒，继续使用既有 Vulkan surface 重建；保持 SDL 原来的音频暂停/恢复行为。
- teardown 在 join guest 前释放生命周期等待；新 boot 保留实际窗口焦点，不把后台重启当成前台。
- shader/pipeline 预热新增非阻塞取消请求，已有 stop 接口仍负责 join 和资源回收。

第一次修复验证后台 CPU 为 **5.88%**，5.10 秒观察区间日志停在同一帧 868，返回前台后同一进程继续到 922 帧。
另一进程连续三次 Home / 返回，后台分别 **4.90%、6.15%、6.31%**，三个周期都恢复出帧。
后台仍保留事件/计时/音频队列等低负载工作，不宣称整个进程完全冻结或所有 guest 时钟都暂停。
这改善后台资源、耗电与多包切换干扰，**不是前台帧率已到 60 的证明**。

测试：`tools/test_app_lifecycle.c` 覆盖前台快路径、多等待者、暂停/恢复、停止、重复 boot/focus；
`test_shader_warm_job.cpp` / `test_pipeline_warm.c` 验证 worker 尚在不可取消调用内时，取消请求立即返回，后续 join 仍完成所有权回收。
ASan/UBSan 生命周期、pipeline warm 和 shader warm background 回归通过；Release/8 Elite 与独立测试包完成构建和诊断隔离检查。
普通/测试包继续使用同一 `GAMELIB_ID=993c0a5c82dc5099` 与现有 O3 游戏库。

已安装的普通 Release APK 为 `005a9ab0672e155dd9d109b9fd375b8b77fbed932fc9fd3dfe37be01a0a61c97`，
运行时为 `8ff87cf82b58c889cf8f98de9947a33e7a5963749a68d03da9696e3efcdb29f8`；
使用同签名覆盖安装，原包 UID、设置/库哈希与存档目录权限保持不变，未卸载或写存档。

包含一次暂停/恢复及另一进程的连续三个切换周期；测试结束均关闭独立测试包。

## 2026-10-30：渲染效率审查

同一草地存档、真实 2×（设置中的分辨率倍率，无 `NO_SCALE`）、60 FPS 目标、20 秒半摇杆转视角，Release/8 Elite 独立测试包。
开关用 `--diagnostic-env` 传入；结果是同场景短测，温控状态与电源单独记录。原始数据在 `.work/render-audit-20261030/`。

| --- | --- | ---: | ---: | --- |
| base-1 | 无 | 18.83 | 63.8 | 0→0 |
| nomut-1 | `LARECOMP_VK_NO_MUTABLE=1`（渲染目标去掉 MUTABLE） | **24.29** | 52.4 | 0→1 |
| nobarrier-1 | `LARECOMP_VK_NO_PASS_BARRIER=1`（不安全测量） | 18.50 | 68.0 | 1→1 |

基线在不同温控下都稳定在约 19 FPS；去掉 MUTABLE 在同温控下高 25–29%，其余方向无收益。

### 原因与修复

所有非深度图像都带 `VK_IMAGE_CREATE_MUTABLE_FORMAT_BIT`，但没有 `VkImageFormatListCreateInfo`。
Mesa Turnip（`tu_image.cc` 的 `format_list_ubwc_possible`）在没有列表时假定可能出现不可压缩格式，直接关闭 UBWC；
Adreno 830 属于 `ubwc_all_formats_compatible` 的 a7xx gen3/a8xx 能力，只要列表里每个格式都支持 UBWC 就会保留压缩。
因此 2× 下的多附件 G-buffer、后处理和所有颜色纹理都在未压缩状态下读写，sysmem 渲染带宽被放大。

直接去掉 MUTABLE 会让游戏的格式重解释视图违规，所以正式修复为：Turnip + Adreno 8xx 上为可变颜色图像附加
`image_format_list.h` 中同兼容类、且都可压缩的全部格式（只排除 E5B9G9R9）；存储图像、深度图像和其他设备不变，
`LARECOMP_VK_FORMAT_LIST=0|1` 可覆盖。旧款 Adreno 遇到混合列表会关闭压缩甚至改线性排布，所以不扩大默认范围。

同一新 APK（`ecb818a9…`，运行时 `4c43388a…`，`GAMELIB_ID=993c0a5c82dc5099`）对照：

| 运行 | 格式列表 | FPS | GPU 忙碌 ms/帧 | 温控 |
| --- | --- | ---: | ---: | --- |
| fl-on-1 | 开（默认） | 20.40 | — | 1→1 |
| fl-off-1 | 关 | 18.97 | — | 1→2 |
| nomut-3 | 关 + 去 MUTABLE | 21.07 | — | 2→2 |
| trace-fl-off | 关，`--timing-trace` | 17.49 | 40.9–42.3 | 1→2 |
| trace-fl-on | 开，`--timing-trace` | 19.12 | **32.6–33.1** | 2→2 |

GPU 每帧忙碌时间减少约 8.5 ms（约 20%），格式列表与去 MUTABLE 的帧率在噪声范围内一致。
帧率提升小于 GPU 降幅：充电升温后 GPU 频率下降，且帧时间已转为受渲染线程（叠加层约 33 ms/帧）和游戏线程等待栅栏限制。
同一存档就绪帧（915）开/关列表截图，差异只在随风摆动的树叶与触控按钮淡入；地面、天空、角色和建筑一致。
`tools/test_image_format_lists.py` 用独立尺寸表核对 46 个颜色格式的整类列表、E5B9G9R9 排除和默认设备条件，并做过删格式的变异检查。

### 剩余瓶颈（尚未修复）

- **渲染线程**：每帧约 4400 次绘制、180 个渲染通道、27 次提交，单线程翻译约 30 ms/帧；其中描述符集约 8 ms
  （缓存只在单次提交内有效，1 ms 拆分使其频繁失效）、顶点复制约 6 ms（约 60 MB/帧）、纹理检查约 3.5 ms、常量缓冲约 3.7 ms。
- **线程同步**：游戏线程每帧仍在 nvnSyncWait 等待约 16–19 ms，GPU 每帧空闲约 19 ms，三段流水没有充分重叠。
- **LRZ 失效**：`TU_DEBUG=perf` 显示大量“FS writes depth or has side-effects”“Depth write + blending”“CmdClearAttachments”，
  需查明翻译器写 `gl_FragDepth`、内存副作用和通道中途清除对早期深度剔除的影响。
- **GMEM 不可用**：全部附件每次 LOAD/STORE、G-buffer 被 1 ms 拆分和 6/8 目标交替打断，强制 GMEM 仅 3.8 FPS。

2× / 60 FPS 仍未达到：GPU 还需再减约一半，渲染线程也需减半并改善重叠。

### CPU 采样（simpleperf，进程内 10 秒，1 kHz）

同一场景格式列表开启后的普通测试中采样（`.work/render-audit-20261030/cpu-*`）：

| 线程 | 占一个核 | 主要热点 |
| --- | ---: | --- |
| 后台 SPIR-V 准备 | 约 87% | `cache_load_at` 44%、zstd 解压、逐字节 FNV 校验；对 48,257 个已缓存模块逐个完整解压验证，持续约 58 秒，`translated=0` |
| 渲染线程 | 约 50% | `memmove` 16%（顶点/常量复制）、`vk_tex` 16%（无页写跟踪时对动态纹理逐帧全量哈希，约 18 MB/帧）、`draw_` 11%、`stage_set` 9% |
| 游戏工作线程 | 各 15–30% | 游戏代码之外，`tegra_layer_size` 占 10–13%：每次 `FlushMappedRange` 在全局锁下遍历全部纹理并重算 mip 链大小 |

已修复写通知扫描：纹理存储大小在描述创建时计算并缓存，游戏线程与渲染线程的两处扫描、纹理变化检测和绘制预检直接使用。
同场景采样中 `tegra_layer_size`（全进程周期 3.95%）消失，写通知路径合计从每 10 秒 1277 个采样降到 414 个；
剩余为链表遍历本身，需要按地址建索引才能继续下降。

同时发现两项与渲染代码无关、却直接限制 CPU 的设备状态：

- 游戏运行时 ColorOS 把 CPU 上限压在性能核 2.23 GHz（额定 3.53）、超大核 1.69 GHz（额定 4.32），偶尔 1.2–1.4 GHz，温控状态仅 0–1。
- 高通性能 HAL 持续报 `Perflock Submit request limit reached`：`media.hwcodec` 自 10-25/10-26 起持有 30 个永不过期的升频请求
  （手机已连续运行近 5 天），新的升频请求被拒绝。本应用视频为 FFmpeg 软件解码，不使用该服务。需重启手机清除后复测频率与帧率。

后台准备的规划阶段每次启动都因“最近使用列表”变化而无法命中收据；运行时源码一变（`SHADER_BUILD_ID` 变化）还会重新翻译数万请求，
GLSL 拼接中 `vfprintf` 占该线程一半时间。它不在帧的关键路径上，短测中开/关帧率无差别（22.74 / 22.66 FPS），
但在功耗和温控受限的手机上持续消耗一个核，属于待优化项。
