## GPU 与等待的定位

在 `gpu-a` 的第 1150 帧记录了 195 个 GPU 时间戳，首尾间隔 27.93 ms。
三个多绘制的六目标 1280×720 阶段分别约 3.062、2.026、1.831 ms；另有一个低分辨率阶段约 2.249 ms。
这是单帧阶段之间的时间差，含中间排序/上传等成本，不等于纯着色器指令时间。

有效窗口内的 GPU 提交时间约 26–27 ms/帧，其中呈现工作约 2.5–2.7 ms；
计数器对中的提交间空档约 9 ms，取帧约 0.04 ms、提交 API 调用约 0.3 ms/帧。
CPU、GPU 与队列等待存在重叠，不能把这些数值相加当作总帧时间。

为使诊断可复现，正式控制器增加：

- `--gpu-profile-frame <绝对帧>`：单帧阶段时间戳，自动开启 profiling。
- `--timing-trace`：提交、计数器配对、等待及最多 64 次 buffer-copy 依赖日志，自动开启 profiling。
- `--render-split-us <0..20000>`：只覆盖长绘制阶段提交阈值；不自动开启 profiling，0 关闭中途拆分。

均记录到 `launch.json`。时间戳回读会等 GPU，诊断结果与普通 FPS 分开；若未运行到指定帧，
不能把缺少 `[gpuprof]` 的报告当作成功取得该帧的 GPU 耗时。

## 缓冲区复制的依赖修正

打开异步复制后，旧诊断的前 64 次等待均指向命令 19（`CMD_SET_RENDER_TARGETS`）：
预检查用 `write 0+UINT64_MAX` 使任意在途复制都触发全局等待。
实际命令只设置捕获的目标状态，附带捕获也只记录 GPU 图像复制，不读写 guest buffer 内容。

现在切换目标无需全局等待；清除操作只检查可能上传的附件范围，计数器只检查 16 字节写入
及相邻前一条计数器的 8 字节时间戳读取。覆盖复制源、读取复制目标和未知命令仍等待。
所有检查都发生在取得接下来使用的命令缓冲之前，避免等待提交后继续使用旧句柄。

修正后等待推进到 `3b62c3600/3b62c3a00 + 0x370` 的绘制前常量缓冲区读取检查。
有效窗口的等待从 2.854 ms/帧变为 2.860 ms/帧，**没有证实净等待收益**。
因此异步复制仍默认关闭；下一步需区分常量缓冲区实际 CPU 读取范围和纯 GPU 消费，
不能继续删除等待来掩盖 GPU→CPU 依赖。

## 长绘制阶段提前提交

原先非高通原厂驱动按 3 ms 阈值拆分长绘制阶段，边界提交另用既有策略。
这会影响 GPU 何时开始执行、后续复制等待多久，以及同一数据重新上传的次数。

关闭中途拆分并未明显减少顶点复制，反而延迟了 GPU 工作：

| 诊断 | 0：不拆分 | 原 3000 µs | 1000 µs |
| --- | ---: | ---: | ---: |
| 有效统计帧数 | 238 | 288 | 376 |
| 每帧提交数 | 11.223 | 13.458 | 22.963 |
| 顶点复制 MiB/帧 | 44.952 | 44.882 | 46.370 |
| buffer-copy 等待 ms/帧 | 5.857 | 3.306 | 1.737 |
| GPU ms/帧 | 28.765 | 29.285 | 25.274 |

同一 APK 的 1 ms 阈值增加约 3.3% 的顶点复制量，将 buffer-copy 等待减少约 47%；
其作用是让长绘制阶段更早与 CPU 翻译并行。上述为诊断数据，普通帧率对照如下。
