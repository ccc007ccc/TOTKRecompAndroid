## 定位与实现

修前诊断明确有两种停顿：前台管线首次构建单帧约 4.1 秒；编译计数为零时，连续帧 GPU 等待
436/398/385/340/356/332/319/311 ms。关闭后台预热没有消除后一类。
多帧 GPU 计时进一步定位到片元着色器 `b9e2681d3cbc73d8`、顶点程序 `247cd9200`，
一次 1600×896 绘制耗 144.662 ms、800×448 绘制耗 38.203 ms。
通道的首个片元程序 `de65…` 不是其中最慢的绘制，不能仅凭通道标签选择修复目标。
现有逐绘制计时行首描述前一个 draw，区间身份以其 `first fs … vs=… fs=…` 字段为准。

正式 Maxwell 翻译器有两个结构化控制流缺口：跳到紧邻下一块仍被判为不支持；嵌套条件提前跳到共同出口时，
递归处理剩余区域丢失了外层 `alt`。两处修复使真实材质不再整段退回大型 `switch(pc)` 循环。
保留不支持形状的原有保守回退，没有删分支、改数值精度或跳过绘制。

同一材质只用 `STL[0]` / `LDL[0]` 一个字，原来每个像素却初始化 256 字局部内存。
上游 [mamcjr/TOTKRecompAndroid，b0948bbf](https://github.com/mamcjr/TOTKRecompAndroid/tree/b0948bbf77099b133029668016b24ad0d1a1d120)
的 `docs/TOTK-PORT.md` 与 `runtime/nvn/maxwell/translate.c` 已描述同一材质、同样的严重掉帧问题（MIT）。
本次采用其按实际访问缩减的思路：只对 RZ 常量地址缩数组，保留原 255 掩码与逐 lane 回绕；
寄存器动态地址继续分配 256 字，不采用未验证的 SPH 动态窗口缩减。因此负偏移、跨 1 KiB 末端和常量别名语义不变。
真实材质缩为 `lmem[1]`；GLSL 和 MSL 声明均更新，生成游戏库 ABI 不变。

合成回归覆盖紧邻跳转、嵌套共有出口、保守回退、零初始化、常量别名、动态窗口、向量和负偏移回绕：
24,576 个独立 CPU 预期值、288 个 GLSL/SPIR-V 校验、16,384 个随 lane 变化的真实 Vulkan 数值通过，
ASan/UBSan 通过，最终 Vulkan 同步验证零告警。首次 GPU 测试因测试设备未开启 shaderInt64 失败，修正声明后才通过。
准确译码身份随修改变化；SPIR-V 缓存仍按准确源码键复用，未重写兼容白名单或清空旧缓存。

## 剩余的约 19 FPS 与编译停顿

修后仍有约 52–54 ms 的稳定帧段。呈现线程 82 每帧在 `WaitForAddress`（SVC 0x34）等待约 49–53 ms，
由主线程 80 的 `SignalToAddress` 唤醒。GPU 同步等待接近零，内部目标 60、请求间隔 3 已被修正为 1。
呈现线程等待多不代表游戏主线程的 CPU 成本很低，不应据此删除同步或关闭 core-0 保护。

默认预热的 20 秒、250 Hz CPU 采样得到 14,759 个样本、无丢样；后台译码/检查约占全进程 CPU 周期 32%，
管线 worker 合计约 33%。累计比例不证明四个 worker 同时编译，不能据此断言编译预算失效。
关闭预热另采 9,281 样本、无丢样，后台成本消失但后段相同 52 ms 信号等待仍在。
该诊断轮 23.457 FPS / p95 60.34 ms / 1% low 4.50 / max 1955.32 ms，温度 30.0→31.0°C、温控 0→0，
AC powered 从 false 变 true；含 CPU 采样和 timing trace，不能拿平均 FPS 与普通轮次相除宣称收益。
两轮 CPU 采样分别有 0.45% / 1.12% 错误调用链，`security.perf_harden` 均恢复原值 1。

等待探针仅在诊断包和 `LARECOMP_LOG_KERNEL_WAITS=1` 下工作，按线程自身 TLS 区分 SVC、core-0 与 host 等待。
进一步跟踪最近唤醒呈现线程的生产者，并记录线程 CPU 时间与宿主 TID。日志在服务锁释放后输出；
没有改变调度或原 `g_blocked_ns` 口径。可选回溯从指定绝对帧开始，每个生产者最多记录四个不同的长等待地址。

### 主线程与工作线程的新证据

`producer-waits-20261031` 确认约 19 FPS 后段主线程每帧 CPU 时间 8–9 ms，SVC 0x34 等待约 42–44 ms；
core-0 条件排队约 0.03 ms、host 等待通常不足 0.2 ms。
本机原版 SDK 符号将最长等待调用点 `sdk+0x13c2c4` 解析为 `nn::os::WaitLightEvent`；
呈现线程的 `sdk+0x13e794` 为 `ReceiveLightMessageQueue`。
`light-event-chain-20261031` 又确认主线程等待事件由游戏线程 126／127 完成，
一次限定回溯为 `main+0x2daa20 → 0x2dad80 → 0x3e55e0/0x3e5dfc → 0x74240 → WaitLightEvent`。
这里的库偏移已用 SHA 匹配的 O3 游戏库符号解析，不能拿另一构建的 native 地址直接套用。

`worker-waits-20261031` 跟踪到 126／127 自身也常等待约 44–47 ms，CPU 每帧约 7–9 ms；
部分事件由线程 128 完成。线程 128 的一个后段窗口每帧 CPU 10.8 ms、地址等待 13.2 ms、core-0 条件排队 0.19 ms，

## 后续修复：省去 core-0 单核线程的重复宿主让步

在运行中只读 SDK `ThreadType`，并核对其 `GetThreadId` 字段后确认：126／127 分别是
`ModuleSystemWorker1/2`，128 是 `BaseProcExecutor0`，129／130 为另外两个 BaseProcExecutor。
名字与 ID 来自存活进程，不仅按创建顺序推断；SDK 名字/指针位于 +0x180/+0x1a0，ID 位于 +0x1b8。

新计时发现原来漏掉的约 30 ms 主要是线程 128 每帧约 300 次 `SleepThread`：一个低帧窗口中，
整次 SVC 每帧 31.394 ms，其中服务本体 31.074 ms，绝大部分成本在 `sched_yield()`。
原来的窄探针只统计条件等待和正时长休眠，不能覆盖这些负值让步。
原版 SDK `YieldThread` 最终明确传入 `-1`；完整 SVC、窄等待桶和线程 CPU 时间互相重叠，不能相加。
20.85 秒 `/proc/<pid>/task/*/schedstat` 快照也保留，读取全局 schedstats 开关被拒，未改系统调度配置。

语义参考为本地 Eden `26a03d2473787abf3223b2d0e65b291eee00c1e1` 的
`src/core/hle/kernel/svc/svc_thread.cpp` 和 `k_scheduler.cpp`：0／-1 是不迁移／允许迁移的主动让步，
没有合适线程时不应反复进行无效调度。本项目实现独立编写，没有复制 GPL 代码。

正式修复只对 **TotK 1.4.3、core-0 保护启用、当前 core 为 0 且 `core_mask==1`、参数为 0 或 -1** 生效。
这类线程不允许迁移 guest 核心，`rt_svc` 已释放所有权并在 FIFO 尾部重新排队，让已排队的其他线程先执行，
因此省去重复的宿主 `sched_yield()`。现有队列、所有权、安全抢占点和亲和性锁仍保留；
其他核心、允许迁移的线程、-2、正时长休眠、关闭 core-0 保护或其他游戏继续使用原路径。
诊断包可用 `LARECOMP_C0_GUEST_YIELD=0` 反向对照，普通 Release 保留修复且不读取该诊断覆盖。

### 进一步分开渲染请求与请求间等待

原 `[hitch]` 的 `other` 有时达到 60–75 ms，既可能含请求间等待，也可能含未归入 EXEC 的回调等工作。
新增诊断开关 `LARECOMP_LOG_RENDER_FRAMES=1`，可配 `LARECOMP_RENDER_TRACE_FRAME` 指定起始完成帧。
它在渲染线程按帧累计 EXEC、present、fence、内存通知、回调和 driver drain 的墙钟，并记录线程 CPU 时间。
`gap` 是墙钟减请求时间，包含队列等待和 bookkeeping，不等于纯 GPU 空闲；CPU 与请求时间也不能相加。
沿用已有请求计时，只在开启时每次呈现多读一次线程 CPU 时钟；超过 50 ms 才输出，每次游戏最多 128 条。
普通 Release 编译掉开关、计数和日志，不改变请求顺序、同步或 ADPF 默认计时。

主机回归覆盖分类、完成帧编号、起始过滤、日志上限、重启和关闭；实际请求队列/录制 worker 的 ASan/UBSan、
真实 Vulkan 同步验证及缓存身份独立性通过。`[render-frame] frame` 与采样完成帧编号相同；
旧 `[hitch] frame` 在呈现计数增加前记录，对应 `frame_times_ms` 的帧号需加 1。
