“固定负载”指当时未经目标缩放的负载，不能当作 2× 成绩；32.67 / 30.74 等数字不代表正常游玩。
此时控制器默认 `GAME_DYNRES=1`，但普通启动默认关闭，原文把二者写成相同默认值不准确。

因此仅在 **TotK 1.4.3 + Turnip + Adreno 8xx** 上默认开启这两条路径。
单独开启纹理队列的收益较小，第二组组合测试的 p95 帧时间反而变差；本轮不代表全场景流畅度或长期画面验收。

## 瓶颈定位

TotK 1.4.3 的呈现已走 `framepace_period_ns()`，测试目标为 60 FPS；旧 `[pace]` 中的
`slow 1` / `pace 30` 是继承的 GPU 计数器策略，不能单独证明锁 30 FPS。
七处控制器补丁与已审核的 [MacNativeGames 控制器](https://github.com/ly05010419/MacNativeGames/blob/f024ef04c707c4b4bb5b6328bfc55ae89642af40/games/totk/runtime/game_patches_v143.c) 一致，
本轮保留已有实测时间步长和补丁。

`--timing-trace` 新增限速、等待命令翻译、排空队列、队列容量/领先帧数等待，以及纹理/采样器更新分类。
`drain` 包含 `texture-drain` / `sampler-drain`，这些分类不能相加；不同线程的工作/等待也可能重叠。
GPU 阶段标签补充首个 VS/FS 地址、输出 mask、实际写入附件和渲染区域，便于核对同一工作负载。

初始 `gpu-trace` 完整统计窗口 313 帧：限速等待不到 0.001 ms/帧，排空队列约 5.85 ms/帧。
后段部分窗口达到约 11.5 ms/帧、40 次排空/帧。进一步分类确认主要来自纹理槽位更新，采样器等待很少。

此前一个低分辨率单次绘制阶段约 2.25 ms，本轮同一片元哈希约 0.066 ms。它对应
`environment_renderer_env`，并且两次的实际区域/分辨率不同。时间戳行包含到下一标记的间隔，
不能把其中的排队/提交空档全部归为着色器指令成本，因此本轮没有据此削减效果或改写该着色器。

## 实现与生命周期

1. 先构造有效的纹理/视图描述符，包括共享纹理对象的独立 swizzle。完全相同时无需写入和排空，
   纹理像素变更仍走独立通知。这是默认开启的等价操作合并；同步模式下 `--texture-reuse off` 可作旧行为对照。
2. 队列路径捕获描述符值，并为新纹理保留引用，然后把更新与命令列表放入同一个请求队列。
   旧绘制继续读旧槽位；后续绘制才看见新值。调用者的视图内存可在返回后重用。
3. 渲染线程只发布槽位并将待释放引用挂到完成链表，不获取 NVN 对象锁。
   游戏线程在锁外收集这些引用，旧槽位继续沿用现有延迟释放；多余的预留引用单独归还。
   这样避免“持有对象锁等待队列，而渲染队列又等待对象锁”的死锁。
4. 纹理池销毁先排空并收集更新，重启在释放纹理/池之前收集；最终清理包不依赖 reset hook 顺序。
   异步渲染关闭时保留同步路径。队列有既有容量限制，容量压力仍允许阻塞生产者。

队列更新由 `--texture-updates queued|sync` / `LARECOMP_TEXTURE_QUEUE=1|0` 对照，
复用新的 `vk_async_call` 和原来的同步回调入口，不增加第二套执行线程。

## 第一组结果与负结果

同一 APK `847729d514c11543ce5ce4cc76f70bdef801fb63dc9cf2cd80e7dd376ea1a760` 的诊断中，
旧路径和仅合并完全相同注册分别约 26.31 / 25.83 FPS。有效窗口中真正相同的注册只有约
0.10 / 0.30 次/帧，实际纹理排空约 17 次/帧：合并重复操作并没有解决主要阻塞。

接入队列后，`queue-trace` 有效窗口 339 帧，纹理排空等待为 0，其他排空约 0.74 ms/帧，
捕获更新约 40.31 次/帧。等待命令翻译及 GPU fence 的时间也变化，不能把消失的排空时间直接当作帧时间收益。

首个队列版本（后续已补充上述对象锁回收策略）的同 APK 普通对照为：

| 模式 | FPS | p95 (ms) |
| --- | ---: | ---: |
| 同步 A1 | 29.00 | 46.94 |
| 队列 B1 | 29.17 | 44.68 |
| 同步 A2 | 25.85 | 48.92 |

该组仍允许游戏动态分辨率。GPU 记录同时观察到 320×180 与 400×224 等不同区域，不能宣称固定负载下的稳定提升。
控制器因此增加 `--game-dynres off`，使用运行时已有的计数器冻结路径，保持游戏的最高分辨率来做独立对照；
常规命令默认仍为 `on`，开关写入 `launch.json`。这不是降低分辨率的优化。

## 固定负载的诊断与普通对照

以下使用同一固化包 `package-final/`：APK SHA-256
`2bd55c26bdf02302f61fb932c6400e41a602fb7b19397dc24228b2eb33acc55c`，运行时 SHA-256
`2a60fc072439425cda93b699495bd85b8db8ffcd62013508d5ac2734c07b01e1`。
源码是 `62eae6e` 加本轮运行时、诊断和控制器改动，此时尚未调整两项功能的默认值。
全部使用 `--game-dynres off --shared-alias off`，等价注册合并保持开启，设备接 AC 电源。

先单独关闭 GPU buffer-copy，用诊断确认纹理等待确实转移：

| 诊断运行 | 完整统计窗口 | 纹理排空 (ms/帧) | 全部排空 (ms/帧) | 等待翻译 (ms/帧) | FPS |

## 默认策略及最终产物

`vk_deferred_resources_default()` 统一判断 TotK 1.4.3、Turnip 驱动和 Adreno 8xx 名称，
满足条件时默认启用纹理队列与 GPU buffer-copy；其他游戏、GPU 或驱动默认关闭。
`LARECOMP_TEXTURE_QUEUE=1|0` / `--texture-updates queued|sync` 和
`LARECOMP_VK_ASYNC_BUFFER_COPY=1|0` / `--async-buffer-copy on|off` 仍可分别覆盖。
要复现本轮同步对照，必须同时指定 `--texture-updates sync --async-buffer-copy off`；
若还要恢复相同注册仍排空的旧行为，再加 `--texture-reuse off`，该开关不改变队列模式。
共享映射 `LARECOMP_VK_SHARED_ALIAS` 仍默认关闭；游戏动态分辨率仍默认开启。

调整默认策略后重新构建并安装 `package-default/`，最终身份为：
